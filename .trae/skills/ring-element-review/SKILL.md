# 圆环代码专项复查

针对本项目 `Harderware/RingElement.c/.h` 及其调用链做只读静态审查。默认不修改固件代码；只有用户明确要求修复时才编辑。若用户要求修复，不得擅自更改已有参数或变量名称。

## 固定上下文

- 图像为 `Image1[GRAY_W][GRAY_H]`，第一维是列 X，第二维是行 Y；尺寸由 `Harderware/Gray.h` 当前定义决定。
- `L_Edge/R_Edge` 以行号为下标、列号为内容，负数表示未找到；第 0 列可以是有效边界，不能用 `> 0` 作为通用有效性判据。
- A/B 单角点标志同时可能被十字和圆环使用，不能仅凭该标志确认圆环。
- `project/mdk/out_file` 中的列表和映射文件可能是旧构建产物，只能作为历史参考，不能证明当前源码编译、链接或调用关系正确。

## 每次复查必须读取

1. `Harderware/RingElement.c` 和 `RingElement.h`。
2. `Harderware/Gray.c/.h` 中边线约定、角点生成及元素状态机调用点。
3. `Harderware/Element.c/.h` 中与圆环共用或重名的函数、十字状态切换条件。
4. 工程文件 `project/mdk/seekfree.uvproj` 中相关源文件的编译包含关系。
5. 用全工程符号搜索确认 `Ring_Statemachine` 的真实调用点，不能只凭源文件加入工程就认定功能已启用。

## 固定检查清单

### 1. 调用链与元素互斥

- 确认图像处理到圆环状态机的真实调用链是否存在。
- 检查十字与圆环是否会在同一帧同时响应、同时改写边线。
- 检查单角点、无角点等候选条件是否有圆环专属几何判据和必要的连续帧确认。

### 2. 状态机可达性与状态保持

- 核对初始状态是否能进入检测分支，各状态是否可达、可退出。
- 检查赋值与相等比较混用、状态编号写错、分支落空。
- 圆环方向等跨帧信息必须持续保存，不能用每次调用都会清零的局部变量承载。
- 入环、环内、准备出环、出环和返回普通状态应形成闭环，并有异常或超时退出路径。
- 检查状态动作函数的返回值是否被调用者处理，补线完成、误判退出和检测失败不能混为一谈。

### 3. 检测阶段变量与计数生命周期

- 所有阶段变量、计数器和历史采样值必须在使用前初始化。
- 分清单帧扫描计数与跨帧确认计数，确认其生命周期与注释语义一致。
- 检查连续计数是否在中断、丢线、换向、状态进入和退出时复位。
- 若实际为累计计数而设计目标是连续段，应作为误判风险报告。
- 检查静态变量是否跨帧、跨圆环或跨左右方向污染。

### 4. 边线有效性与左右镜像

- 统一使用负数表示无效，避免把第 0 列有效边线误判为丢线。
- 对照左右圆环的扫描方向、断裂侧、恢复条件、斜率符号和补线方向，确认镜像一致。
- 区分真实镜像差异与无意的偏移、阈值或有效性判断差异。

### 5. 图像与边线数组边界

- 逐个验证 `Image1[x±k][y±m]` 的横纵下标范围和循环起止条件。
- 检查无符号循环变量递减下溢，以及坐标加偏移后的上溢或越界。
- 检查 `L_Edge/R_Edge[Y]` 的 Y 范围；公共函数若依赖调用者保证范围，要核对所有当前调用点。
- 未发现越界时只写“当前路径未发现明确越界”，不要声称已证明所有输入绝对安全。

### 6. 补线锚点、斜率与退出趋势

- 锚点必须有效，不能使用未找到点或默认零坐标参与计算。
- 斜率计算必须避免除零，并核对坐标系、符号和左右镜像方向。
- 趋势检测首次采样不得与静态零值直接比较而形成虚假跳变。
- 左右趋势计数不得无意共享；新帧、新状态及趋势中断时应按设计复位。

### 7. 声明、定义与链接一致性

- 搜索圆环相关函数在 `RingElement.c` 与 `Element.c` 中是否存在重复外部定义。
- 核对头文件声明、函数定义与调用签名是否一致。
- 确认相关源文件是否同时参与工程构建；同时构建且存在同名外部定义时，报告重复公共符号风险。
- 文件内专用函数应有可见的前置声明或合理定义顺序，避免依赖隐式声明。

### 8. 角点坐标的新鲜度

- 确认 A/B 坐标仅在对应角点找到时更新，还是每帧清零。
- 状态确认帧之后继续使用 A/B 坐标时，检查是否缓存了有效触发坐标，或验证了当前帧坐标仍有效。
- 过期坐标只能作为明确设计的历史锚点，不能无条件当作当前角点。

## 输出要求

- 先说明本轮审查范围，以及圆环逻辑当前是否真实参与运行。
- 按“明确 BUG / 风险与设计缺口 / 本轮未发现问题”分类，按严重度排序。
- 每个问题给出可点击的文件行号、触发路径、实际后果和最小修复建议。
- 明确区分源码事实、由事实推出的行为，以及需要上车或日志验证的猜想。
- 复查时指出上次问题是否仍存在，并单列本轮新增或修正的结论；不要仅复述上次报告。
- 默认只读，不修改固件代码，不主动创建额外审查报告文件。
